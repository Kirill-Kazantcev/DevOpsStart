# Лабораторная работа №1: Docker и Docker Compose Best Practices

## Цель работы
Изучить анти-паттерны и best practices при работе с Docker и Docker Compose, научиться писать оптимальные Dockerfile и docker-compose.yml с сетевыми изоляциями.

## Структура проекта
``` marcdown
lab1/
├── docker/
│ ├── app/
│ │ └── index.html              # HTML приложение
│ │ 
│ ├── bad.Dockerfile            # Плохой Dockerfile
│ └── good.Dockerfile           # Хороший Dockerfile
│ 
├── compose/
│ ├── app/
│ │ ├── Dockerfile              # Dockerfile для compose
│ │ └── index.html              # HTML приложение
│ │ 
│ ├── .env                      # Файл с секретами
│ ├── bad-docker-compose.yml    # Плохой compose
│ └── good-docker-compose.yml   # Хороший compose
│ 
├── scripts/
│ ├── build-and-run.sh          # Скрипт сборки и запуска
│ ├── test-isolation.sh         # Скрипт тестирования изоляции
│ └── cleanup.sh                # Скрипт очистки
```

## Часть 1: Dockerfile

### 5 плохих практик в `bad.Dockerfile`

| № | Плохая практика | Почему плохо | Исправление | Результат |
|---|----------------|--------------|-------------|-----------|
| 1 | **Раздельные RUN** (`apt-get update`, `install`, `clean` отдельно) | Каждый RUN создает слой. Кэш apt остается в промежуточных слоях, даже после `apt-get clean`. Размер образа ~367MB | Использование официального `nginx:1.25-alpine` с объединенными командами | Размер ~74MB (экономия 80%) |
| 2 | **Копирование всего контекста** (`COPY .`) | Копируются `.git`, временные файлы, секреты и другие ненужные файлы, увеличивая размер образа и риск утечки данных | `COPY ./app` + `.dockerignore` | Только нужные файлы, безопаснее, быстрее сборка |
| 3 | **Запуск от root** + лишние порты | При монтировании томов файлы создаются с правами root на хосте. Лишние порты (443,8080,3000,5000) вводят в заблуждение | `USER appuser` (UID 1000) + только `EXPOSE 80` | Безопасность (принцип минимальных привилегий), четкость конфигурации |
| 4 | **Отсутствие HEALTHCHECK** | Нельзя определить, жив ли контейнер. `docker ps` показывает `Up`, даже если nginx упал. Оркестратор не может перезапустить неработающий контейнер | `HEALTHCHECK --interval=30s --timeout=5s --start-period=5s --retries=3 CMD wget --spider` | Автоматический мониторинг состояния, возможность авто-восстановления |
| 5 | **CMD без обработки сигналов** (`CMD ["nginx"]`) | Контейнер не получает SIGTERM корректно при остановке, может не успеть завершить активные соединения. Время остановки может достигать 10+ секунд | `CMD ["nginx", "-g", "daemon off;"]` | Быстрое (<1с) и корректное завершение, graceful shutdown |


## Часть 2: Docker Compose

### 5 плохих практик в `bad-docker-compose.yml`

| № | Плохая практика | Почему плохо | Исправление |
|---|----------------|--------------|-------------|
| 1 | **Пароль в `environment`** | Секреты (пароли, токены, ключи) попадают в Git-репозиторий, видны в истории коммитов. При `docker inspect` пароль отображается в открытом виде. Может быть виден в логах CI/CD | `.env` файл + `env_file:` в compose. `.env` добавляется в `.gitignore`. Секреты передаются через переменные окружения, но не хранятся в коде |
| 2 | **`network_mode: host`** | Нет сетевой изоляции между контейнерами и хостом. Конфликт портов: контейнер и хост не могут использовать один порт. Не работает DNS-резолвинг между контейнерами по именам. Контейнеры видят все сетевые интерфейсы хоста | Отдельные bridge сети с разными подсетями. Каждый сервис в своей сети. DNS работает внутри сети, контейнеры не видят друг друга |
| 3 | **Нет `restart` policy** | При падении контейнера (ошибка приложения, OOM, сбой) он не восстанавливается автоматически. При перезагрузке хоста контейнер не запускается. Сервис будет недоступен до ручного вмешательства | `restart: unless-stopped` - перезапуск при падении, кроме случая явной остановки. Альтернативы: `always`, `on-failure` |
| 4 | **Нет лимитов ресурсов** | Один контейнер может потребить все ресурсы хоста (CPU, RAM), что вызовет отказ соседних контейнеров (эффект "шумного соседа"). Может привести к краху Docker daemon | `mem_limit: 256m` - жесткий лимит RAM. `mem_reservation: 128m` - мягкий резерв. `cpus: '0.5'` - лимит CPU (половина ядра). Контейнер не может превысить эти значения |
| 5 | **Нет `healthcheck`** | Оркестратор (Docker Swarm, Kubernetes) не может определить, работает ли приложение реально (не только процесс, но и логика). Контейнер может быть в статусе `Up`, но приложение не отвечает на запросы | `healthcheck: test: ["CMD", "curl", "-f"]` - проверка HTTP эндпоинта. При провале healthcheck контейнер считается unhealthy и может быть перезапущен |


## Изоляция контейнеров

### Как добились изоляции

Изоляция контейнеров в файле `good-docker-compose.yml` достигнута следующим образом:

**1. Создание двух отдельных сетей**

В секции `networks:` мы объявили две независимые сети: `net1` и `net2`. Для каждой сети указали свой драйвер `bridge` и уникальную подсеть через параметр `ipam`:

- `net1` использует подсеть `172.20.0.0/24`
- `net2` использует подсеть `172.21.0.0/24`

**2. Подключение каждого сервиса к своей сети**

- Сервис `app1` подключен только к сети `net1`
- Сервис `app2` подключен только к сети `net2`

У каждого сервиса нет доступа к сети другого сервиса.

**3. Отсутствие общих сетей**

Сервисы не имеют общей сети, через которую могли бы взаимодействовать. Каждый сервис изолирован в своем сетевом пространстве.

### Принцип изоляции

Принцип работы этой изоляции основан на том, как Docker обрабатывает сетевые взаимодействия:

**DNS-резолвинг.** Docker встроенный DNS-сервер резолвит имена контейнеров только в пределах одной сети. Когда `app1` пытается обратиться к `app2` по имени, DNS-сервер в сети `net1` не знает о существовании хоста `app2`, потому что этот хост находится в другой сети `net2`. В результате запрос завершается ошибкой "bad address".

**Маршрутизация.** Docker создает отдельный bridge-интерфейс для каждой сети. Между разными bridge-сетями нет маршрутов по умолчанию. Даже если `app1` узнает IP-адрес `app2` (например, 172.21.0.2), пакет не сможет найти маршрут к этой подсети, так как в таблице маршрутизации контейнера `app1` отсутствует запись для сети 172.21.0.0/24.

**L2-изоляция.** Каждая bridge-сеть работает как отдельный виртуальный коммутатор. Трафик внутри одной сети не попадает в другую сеть, даже если они находятся на одном физическом хосте.

### Проверка изоляции

Изоляция подтверждается следующими проверками:

1. `docker exec app1 ping app2` → ошибка "bad address" (DNS не резолвит имя)
2. `docker exec app1 ping 172.21.0.2` → ошибка "Network is unreachable" (нет маршрута к подсети)
3. `docker exec app1 ip route` → в выводе отсутствует маршрут к сети 172.21.0.0/24

### Доступность через хост

При этом контейнеры остаются доступными с хостовой машины через проброшенные порты:
- `app1` доступен на `http://localhost:8081`
- `app2` доступен на `http://localhost:8082`

Это происходит потому, что Docker создает правила в iptables, которые перенаправляют трафик с портов хоста на порты контейнеров, но это не нарушает изоляцию между самими контейнерами.
